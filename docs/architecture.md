# Backend architecture

The backend uses FastAPI as its HTTP boundary and Pydantic models for validated settings and data contracts. `app/api` contains route handlers; `app/models` contains API schemas; `app/services` is reserved for application use cases; `app/integrations` contains external provider adapters; `app/core` owns settings, logging, and shared error mapping.

The Nebius adapter calls the Token Factory chat-completions endpoint over HTTPS using configurable base URL, model, key, timeout, token limits, prompt-size estimate, and process-local in-flight limit. Credentials use Pydantic `SecretStr` and are sent only in the authorization header. Logs contain bounded model/status/latency/token metadata, never request messages, headers, provider bodies, or reasoning text. The client does not retry. It rejects over-budget requests before sending and distinguishes completed, truncated, empty, malformed, timeout, and provider-error outcomes. Only `finish_reason=stop` with non-empty content is accepted as a completed response; task planning then parses its schema and validates evidence. The prompt-size check is a conservative heuristic, not a provider tokenizer or billing limit.

The service exposes `GET /health`; the model client is independently testable with `httpx.MockTransport`. No shell execution or repository-writing agent is included. The local Next.js dashboard talks through a loopback-only route proxy.

## Repository intelligence

`POST /api/v1/repositories/analyze` accepts a configured repository ID, never a path. IDs map through `AUTHORIZED_REPOSITORIES` to absolute roots supplied by the operator. `RepositoryScanner` walks with bounded file count, per-file and aggregate bytes, traversal depth, and processing time. It skips secret paths, generated directories, binaries, and all symlinks. Python is parsed with `ast`; TOML, INI, requirements, and lock manifests are parsed as data. Target code is never imported or executed. Results contain repository-relative POSIX paths and line references, not absolute root paths.

Inference provider selection is explicit through `INFERENCE_PROVIDER=nebius|mock`; the application default is `mock`, even with an API key configured. The Nebius client itself also requires explicit opt-in. The mock provider is deterministic and offline, labels results with `provider=mock` and `is_mock=true`, and never claims Nemotron provenance. Nebius failures are returned as errors; there is no mock fallback. Completed plans include an additive `inference_diagnostics` object with provider, reported/requested model identity, completion status, finish reason, latency, and usage counts when supplied. No reasoning content is returned.

## Engineering task planning

`POST /api/v1/tasks/plan` accepts a configured repository ID and a 10–4,000 character task description. `TaskPlanningService` runs the existing bounded scanner, selects a bounded context of files, modules, AST symbols, imports, manifest entries and test paths, and calls the already configured `InferenceService`. The provider must return a JSON `PlanGeneration`; Pydantic validates its structure before evidence checks run. No source is executed or changed.

Every cited source reference must match a function, class, or import reference emitted by repository analysis. Relevant and expected-change paths must exist in that analysis. Unsupported references are returned in `unsupported_references` and downgrade a plan to `insufficient_context`. Clear harmful task intents are rejected before inference, and repositories without analyzed Python modules return `insufficient_context`. Plans remain `not_started` and require human approval. Provider errors are surfaced; the planner never switches providers after failure. `TASK_PLANNING_TIMEOUT_SECONDS` and `TASK_CONTEXT_MAX_CHARS` bound planning work.

The mock provider supports only the three synthetic evaluation scenarios documented in setup. Unknown or ambiguous tasks return `unsupported`, with no steps or claimed files. These tests measure deterministic schema and evidence handling, not model reasoning accuracy.

The configured live model is `nvidia/Nemotron-3_5-Lightning` at `https://api.tokenfactory.nebius.com/v1/`. Connectivity and a complete structured answer are separate checks; an HTTP success with `finish_reason=length` is not a usable plan.

Task planning asks for a compact JSON plan (up to 4 steps, 5 relevant files, 5 references, 4 risks, 4 validation requirements, and 3 assumptions). For the exact configured `nvidia/Nemotron-3_5-Lightning` model, it requests Token Factory JSON mode (`response_format: {"type":"json_object"}`). JSON mode guarantees JSON syntax only; Pydantic schema validation and source-reference validation remain required. The Nebius OpenAPI describes `response_format` and supports `json_object` (not JSON Schema enforcement).

`NEBIUS_PLANNING_DISABLE_THINKING` defaults to `false`. When explicitly enabled, only task planning for the exact configured `nvidia/Nemotron-3_5-Lightning` model passes `chat_template_kwargs: {"enable_thinking": false}` inside Token Factory's `extra_body`. NVIDIA documents the model-specific control for Nemotron 3.5 Lightning; the effect on Nebius's hosted deployment remains unverified until a live request. Smoke tests and mock inference are unaffected. Provider rejection is returned as a sanitized error with no retry or fallback. Output limits, schema/evidence validation, human approval and read-only behavior remain unchanged.

## Safe code proposals (Phase 4B)

`POST /api/v1/proposals/create` accepts a repository ID and a server-generated task ID. The plan must still be present in the bounded, process-local task store, be a `planned` mock task, require human approval, remain `not_started`, cite `package/calculator.py`, and describe the predefined division-by-zero scenario. The service re-analyzes the authorized repository and checks the source revision hash captured when the plan was created. A mismatch fails with a conflict; the client cannot submit arbitrary patch content or a filesystem path.

The generator supports only the fixture calculator source and a fixed change that raises `ValueError("denominator must not be zero")`. It creates a unified diff in memory and never writes the repository. Static checks validate a single relative path, reject traversal and sensitive paths, check patch headers and hunk counts and size, parse the proposed source with `ast`, and check the expected guard structure. It does not import or execute the fixture. The proposal is returned in `awaiting_review` with `human_approval_required=true`, `provider=mock`, `is_mock=true`, and runtime status `not_run`. `GET /api/v1/proposals/{proposal_id}` retrieves a recent proposal from process memory; restart or eviction can remove it. No approval, apply, or reject endpoint exists.

The future `IsolatedRuntimeValidator` protocol is an interface only. A real validator must run in a disposable sandbox with no host filesystem mounts beyond a read-only source snapshot, no credentials, no network by default, a non-privileged identity, strict CPU/memory/process/output/time limits, and destruction after each run. The sandbox must receive only a size-bounded patch and source snapshot; it must not write back to the authorized repository. Until such a trusted executor is provided, all runtime checks remain `not_run`.

## Local review and handoff (Phase 5A)

`ENABLE_LOCAL_REVIEWS` defaults to `false`; settings reject enabling it unless `ENVIRONMENT=development`. `GET /api/v1/reviews/status` reports the local flag to the dashboard. Decision submission and history routes are available only when enabled and the direct client address, request host, and any browser `Origin`/`Referer` are loopback. Cross-site fetch metadata is rejected. Forwarding headers are not used as identity. The dashboard proxy calls the API over loopback. This is a local prototype boundary, not authentication: the submitted reviewer identifier is only an unverified label and must not be treated as a person, role, or signed identity.

`POST /api/v1/reviews` requires a justification, reviewer label, decision (`approve`, `reject`, or `request_changes`), current proposal version, source SHA-256, and diff SHA-256. At review time the service re-reads the authorized proposal target and checks both hashes. The only transitions from `awaiting_review` are to `review_approved`, `rejected`, or `changes_requested`; a second decision conflicts. `review_approved` means accepted for further consideration only. It does not authorize execution, patch application, merging, or deployment. No `applied` state or apply endpoint exists.

Review and audit records are bounded in-memory data. They are neither durable nor tamper-proof and disappear on restart or eviction. Audit events include accepted decisions and rejected stale/conflicting submissions, with the unverified reviewer label, previous and new states, justification, hashes, static validation evidence, and a sanitized reason. The application does not persist credentials or repository source in these records; credential-like values in review text are rejected.

`POST /api/v1/handoffs` creates a report from the current authorized static scan, stored task plan, proposal, and any review records; `GET /api/v1/handoffs/{report_id}` retrieves it from bounded memory. These endpoints are also loopback-only. Report generation is deterministic and does not call an LLM or cause a review decision. Report sections identify static facts, mock-generated plan/proposal content, unverified reviewer labels, assumptions, unsupported evidence, outstanding questions, and pending next actions. Current source hashes are rechecked; stale proposals are marked stale and called out as a risk. Runtime validation remains `not_run`.

Future public or team use requires real authentication, reviewer identity verification, role-based authorization, durable append-only audit storage, retention controls, and a separately reviewed execution boundary. This phase does not provide those controls and must not be exposed as a production approval service.

## Runtime validation authorization and evidence (Phase 5B)

Runtime validation has a separate `ENABLE_ISOLATED_RUNTIME_VALIDATION=false` setting. Pydantic settings reject enabling it outside `ENVIRONMENT=development`. The status endpoint and write/evidence routes require the direct request to be loopback (including host and browser origin checks); forwarding headers do not establish identity. The separate execution authorizer is an unverified local label and a purpose statement, not authentication or a second person's approval. Runtime attempts are limited to the reviewed, current, statically validated mock proposal for repository ID `planning-fixture`, target `package/calculator.py`, and fixed test case `calculator_unit_tests` / command ID `calculator_pytest_suite_v1`. The request cannot supply a shell command, test path, image, or filesystem path. Authorization is bound to proposal version, source SHA-256, and diff SHA-256, and only one attempt is accepted per proposal revision.

`GET /api/v1/runtime-validation/readiness`, `POST /api/v1/runtime-validation`, and `GET /api/v1/runtime-validation/{evidence_id}` provide readiness, authorization/evidence, and retrieval. The API reads only the two fixed allowlisted files into a bounded in-memory snapshot after all review/hash checks; it rejects links/reparse points and an altered synthetic test. An eventual executor interface receives bytes and a patch, not host paths. Logs, failure details, and paths are bounded and sanitized. The original repository is never a writable target. Evidence and one-time reservations are bounded/process-local and disappear on restart, so they are not durable audit records.

The production executor in this checkout is `UnavailableSandboxExecutor`: it reports host/flag/Docker/image/executor checks and never starts a process. On the current Windows environment, no Docker CLI, verified immutable local image, or hardened executor is configured; readiness is unavailable. A test-only fake executor exercises orchestration branches but does not execute the synthetic repository. Thus no sandbox execution, successful runtime test, or runtime validation is claimed. Before implementing a real executor, review a dedicated Linux worker/container boundary for no network, no credentials, no host mounts, non-root identity, dropped capabilities, read-only root filesystem, seccomp/AppArmor, resource/process/output/time quotas, pinned local image digest, patch application inside the disposable boundary, and verified cleanup. Container isolation still shares a host kernel and is not a complete security boundary. No fallback to host execution is permitted.
